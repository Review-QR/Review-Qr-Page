# Trustit — Deep UI/UX & Wiring Audit (2026-11-16)

Scope: customer app (mobile + web), merchant web dashboard, admin panel, rider app.
Method: static analysis of component structure, button wiring, API route coverage, auth/guard layers.

## 1. Customer App (mobile + web)

### What works well
- **Clean modular design.** 7 dedicated components (`CustomerHomeAndDiscovery`, `CustomerStorefrontAndVerticals`, `CustomerCheckoutAndAddresses`, `CustomerOrdersAndSupport`, `CustomerOnboardingModals`, `CustomerProfileAndSettings`, `BahraichInteractiveMap`) — each with clear responsibility.
- **Auth flow is secure.** `verify-otp` route uses httpOnly cookie + session token, rate-limits at 25/10min, supports Google 1-tap, phone-OTP, email-OTP, and profile-creation with verified-account overwrite protection.
- **Checkout handles the hard cases.** Single-store cart conflict guard, out-of-stock rules, payment retry (stock-hold), 4-digit handover PIN, saved-address book with GPS pin-drop, delivery scheduling slots, rider tip, promo code, UPI/online/COD choice.
- **Store cards are honest.** "Currently not expecting the order" state disables the card and greys it out. Verified badge + live ETA + distance + open status all computed client-side.
- **Loyalty wired end-to-end.** Points card in header, live INR value (350 pts = ₹100), `onRequestLogin` CTA when unauthenticated, and `/api/customer/points` with full session-identity verification (cross-checks customerId, phone, email).
- **Bilingual (EN/HI) UI** via a `t(lang, en, hi)` helper used throughout.

### Issues found
- **[High] Customer app is one 2,968-line monolith.** `app/order/order-portal-client.tsx` orchestrates all 7 customer components + all modal state + bottom tab + GPS + cart + points. This is the single biggest maintainability risk in the customer experience. Any change ripples across 3k lines.
- **[Med] Empty-state & error-surface coverage is thin on customer side.** Only the store grid has a "No stores match" empty state. The checkout sheet, orders list, and address book need explicit empty/error/loading skeletons.
- **[Low] `POPULAR_SEARCH_SUGGESTIONS` rotate on a 2.8s timer** that's not tied to user focus — wastes cycles on mobile and can flicker behind the input.
- **[Low] "Smart Parcha" CTA button** is prominent in 2 places (home hero + banner) but there's no visible confirmation that the OCR/quote flow is actually wired to an API — it's a prop callback that the portal must implement. Verify in integration.

## 2. Merchant Web Dashboard

### What works well
- **Comprehensive module surface.** 13 dashboard modules (dashboard, business, orders, products, qr, standees, reviews, messages, analytics, subscription, payments, profile, support) plus fleet and menu sub-modules.
- **QR actions use modern web APIs.** `navigator.share` for share, programmatic `<a download>` for PNG, `window.print()` with print CSS. No dead-end buttons.
- **Plan-gating is real.** `plan-rules.ts` restricts routes and QR-template count by tier (Basic 2 / Standard 5 / Premium 8) and hides menu/messages/orders from Basic.
- **Orders console has full lifecycle wiring.** 7 distinct fetch calls (`/api/hyperlocal/orders` GET/POST/PATCH, `/api/hyperlocal/tokens`) — all buttons map to real endpoints.
- **Payment / payout module is thorough.** Daily settlements + passbook + KYC + penny-drop bank link + CSV export + print + 4-tab switcher — 21 buttons all with handlers.

### Issues found
- **[High] 3 files are very large and should be split.** `business-profile-form.tsx` (1217), `orders-console-client.tsx` (1174), `occasion-studio.tsx` (1159), `message-designer.tsx` (1132), `merchant-payouts-client.tsx` (1006). Each is past the "one screen" mental-model threshold.
- **[Med] `merchant-console-client.tsx` is the dashboard shell** (672 lines) and renders module sub-pages client-side via a tab state. Fine for now, but as modules grow the routing becomes fragile — consider real routes per module.
- **[Low] No global error boundary in the dashboard.** A single failing module (e.g., `analytics` data fetch) takes the whole shell down. Wrap each module render in an error boundary.

## 3. Admin Panel

### What works well
- **Server-rendered with proper auth.** `admin/page.tsx` uses `requireActiveAdmin()` + `createSupabaseServerClient()` — no client leakage.
- **Sub-app routing is clean.** `/admin/riders` is a 5-line redirect to `/admin/hyperlocal?tab=riders`. No dead pages.
- **Hyperlocal admin client is wired end-to-end.** 25 buttons, all with `onClick` handlers. 5 tabs (orders, settlements, riders, points, + view mode) with proper polling on view change.
- **Customer-points admin route** has a migration-availability check that returns a clear error message instead of a 500 crash.
- **Search input sanitization.** `.replace(/[%_,()]/g, "")` before building `or(...)` filters — protects from SQL-injection via PostgREST `or` syntax.

### Issues found
- **[Med] No admin audit trail.** Settlement/approve/reject/settled actions against orders and payouts are irreversible money moves. Every such button should log actor + timestamp + before/after to an `admin_audit_log` table.
- **[Low] Admin `page.tsx` catches all errors** with a generic "Unable to load business data." — fine for UX, but log the real error server-side so support can debug.
- **[Low] No RBAC granularity.** `requireActiveAdmin` is all-or-nothing. If multiple admins exist, you need role levels (viewer / operator / super).

## 4. Rider App

### What works well
- **49 screen components** under `app/rider/components/screens/`, mounted via a data-driven `screens` array (not a fragile switch). Each screen has explicit `onBack` / `onAccept` / `onDecline` / `onComplete` handlers with sensible fallbacks (`screens[6]`).
- **Rich real-world flows.** Siren radar, slide-to-accept, multi-order batch, merchant-delay compensation, cash ceiling, SOS, helmet selfie, breakdown rescue, pharmacy-Rx pickup, heavy-grocery crate, fragile-cake guard, last-100m landmark, railway-halt reroute, digital fleet ID, in-app masked chat.
- **Rider session is secure.** `rider-session.ts` signs/verifies tokens, and the `/api/hyperlocal/rider` route enforces rate limits + admin-context fallback for critical operations.
- **Dispatch engine is real.** `dispatch-engine.ts` handles cascading radar + timeout/decline handoff — not just a status toggle.
- **Payouts + settlements decoupled.** `settlement-service.ts` + `rider-fleet-engine.ts` (wait-comp, doorstep refund, parking toll, GPS heartbeat, passbook) — money flows are audited.

### Issues found
- **[Med] `rider/page.tsx` is 1,522 lines** orchestrating 49 screens + GPS + audio + onboarding history stack. Same "monolith" risk as customer portal. Split into screen-groups (onboarding / active-order / passbook / profile).
- **[Low] Numeric screen IDs are human-readable** (`id: 48`, `id: 7`) but the `ONBOARDING_SCREEN_IDS` set is hand-maintained. A new onboarding screen requires updating the Set. Add a derived assertion test.
- **[Low] GPS watch-position errors are logged but not surfaced.** Rider sees no "GPS lost — location may be inaccurate" toast. Add a UI hint when `watchPosition` has errored.

## 5. Cross-Cutting Findings

### ✅ Strong (all 4 surfaces)
- **Every button has a handler.** No dead buttons found across ~200 buttons scanned in the main UI files.
- **No orphaned API routes.** All 33 API routes are referenced by at least one UI file. No dead endpoints.
- **No `href="#"` dead links** in customer/merchant/admin/rider UI.
- **Console noise is legitimate.** Remaining `console.log/error/warn` are error-boundary and GPS-fallback paths, not debug leftovers.
- **Auth guards are consistent.** `httpOnly` cookies, `enforceRateLimit` on every sensitive route, `getActiveAdminContext` on admin routes, `verifyCustomerSessionToken` on customer routes.

### ⚠️ Systemic issues to fix
1. **Monoliths.** 3 files > 1000 lines that orchestrate whole app surfaces: `order-portal-client.tsx` (2968), `rider/page.tsx` (1522), `business-profile-form.tsx` (1217), `orders-console-client.tsx` (1174), `occasion-studio.tsx` (1159). Split each into sub-components / hooks.
2. **No global error boundaries** in the dashboard / admin / rider shells. One failing sub-module takes the whole shell down.
3. **No admin audit log** for irreversible money moves.
4. **Thin empty-state / error-surface coverage** on customer side.
5. **Line-endings.** 325 files have CRLF↔LF diffs (already discussed earlier in the session).
6. **`package.json` name is still `review-qr` v0.1.0** — stale.
